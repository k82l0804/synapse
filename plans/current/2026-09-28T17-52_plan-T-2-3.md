## Context

With T-2-1 and T-2-2 complete, `synapse.db` exists, products can be registered, and
signals can be parsed. The daemon engine is the next layer: a process that wakes up,
reads pending runs from the DB, spawns specialist subprocesses for the next step, reads
their signals, and advances state. This is a serial state machine — no parallelism,
no event loop complexity. Steps are synchronous from the daemon's perspective: spawn,
wait, read signal, transition.

## Deliverables

### D-1: Daemon entry point and startup recovery

**Files to change:**
- `src/daemon/index.ts` — NEW FILE — `startDaemon(): void`
- `src/cli/index.ts` — UPDATE — wire `daemon` command to `startDaemon()`

**Implementation notes:**
- On startup: open DB, scan `pipeline_runs` for runs with `status = 'running'`
- For each: set `status = 'stopped'` (no auto-resume by default)
- Log: `[daemon] recovered N interrupted runs → stopped (use synapse resume to continue)`
- Then enter the main poll loop

### D-3: Step executor — spawn specialist subprocess

**Files to change:**
- `src/daemon/executor.ts` — NEW FILE — `executeStep(db, run, step): ExecutionResult`

**Implementation notes:**
- Maps step name to skill name and specialist (`agy` or `grok`)
  ```
  task-review   → agy  → task-review skill
  make-plans    → agy  → make-plans skill
  plan-review   → grok → plan-review skill
  implement     → agy  → implement-plan skill
  test-cycle    → agy  → run-tests skill
  code-review   → grok → code-review skill
  triage        → agy  → review-triage skill
  ```
- Spawns `agent-job.sh <specialist> <skill>` as a child process
- Captures stdout/stderr to a log file in `.synapse/run/logs/{run-id}-{step}.log`
- Waits synchronously for exit (no timeout in MVP — specialist has its own `JOB_TIMEOUT`)
- Returns: `{ exitCode, outputPath }` where `outputPath` is the artifact the specialist wrote

**Spec contract ref:** AC-2, HLT-3

### D-4: Signal reader integration — read artifact, update DB state

**Files to change:**
- `src/daemon/executor.ts` — UPDATE — call `parseSignal(outputPath)` after step exits
- `src/daemon/state.ts` — NEW FILE — `applySignal(db, run, signal): void`

**Implementation notes:**
- After step subprocess exits: call `parseSignal(outputPath)` from T-2-1
- `applySignal`:
  - `DONE`: advance `current_step` to next in sequence, stay `running`
  - `PARTIAL`: advance step, log warning
  - `FAILED` or absent: set `pipeline_runs.status = 'TASK_FAILED'`, set `failure_reason`
  - Write result to `signals` table
- Gate steps (`plan-review` verdict = `APPROVE` needed, `task-review` always gates):
  - If step is a gate step: set `pipeline_runs.status = 'waiting'`, write WAITING file

**Spec contract ref:** AC-3, AC-4, HLT-4, HLT-5
